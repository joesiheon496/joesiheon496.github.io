## 한 줄 요약

> **모델이 코드를 쓰면 병목이 작성에서 검증으로 옮겨간다. 그런데 검증은 함정 목록을
> 외우는 일이 아니라 검사를 설계하는 일이고, 그 종류는 여섯이다.**

크래시하는 버그는 쌉니다. 컴파일러나 segfault 가 알려줍니다. 비싼 것은 **조용히 틀리는**
것입니다. 그림이 나오고 숫자가 나오는데 값이 틀립니다. 모델이 쓴 코드에서 특히 잘
나옵니다 — 문법은 완벽하니까요.

흔한 대응은 "함정 목록을 외운다" 입니다. 그게 왜 부족한지부터 보겠습니다.

## 🚨 시작은 클로드가 틀린 기록입니다

이 글을 시작할 때 클로드가 대표 예시 넷을 들었습니다. 전부 "널리 알려진 사실" 로
통하는 것들입니다. 그리고 글을 쓰기 전에 실제로 컴파일해서 재봤습니다.

**넷 다 틀렸거나 과장이었습니다.**

| 클로드가 말한 것 | 실측 | 무엇이 잡아냈나 |
|---|---|---|
| `(a+b)/2` 가 200·100 에서 **127** 이 된다 | **150** | **두 경로 대조** — 한 줄과 두 줄을 나란히 재니 128 은 두 줄 쪽이었습니다 |
| `step != cols` 는 **정렬 패딩** 때문 | 폭 640·641·643·1000 전부 패딩 없음 | **극단·퇴화** — 홀수 폭까지 훑으니 패딩이 없었습니다 |
| `at<>` 루프가 행 포인터보다 **10\~50배** 느리다 | Release 에서 **1.52배** | **두 경로 대조** — Release 와 Debug 를 따로 쟀습니다 |
| Eigen 식 `auto` **dangling** 이 OpenCV 에도 있다 | 정상값 **7** | **불변량** — `m.u == nullptr` 로 소유권을 봤습니다 |

여기서 중요한 건 넷이 틀렸다는 사실이 아닙니다. **넷을 잡아낸 것이 C++ 지식이 아니라
오른쪽 열의 검사**라는 점입니다. 목록을 외웠다면 저 넷이 목록에 그대로 들어갔을
겁니다 — 틀린 채로.

그래서 이 글은 함정 목록이 아니라 **검사 여섯 종류**로 씁니다. 각 절이 검사 하나이고,
그 아래 숫자는 전부 그 검사를 실제로 돌려 나온 값입니다.

| 검사 | 한 줄 정의 | 이 글에서 잡은 것 |
|---|---|---|
| [1. 두 경로 대조](#1-두-경로-대조) | 같은 일을 두 가지 방법으로 하고 답을 맞춰본다 | 포화, ROI stride, 빌드별 성능 |
| [2. 극단·퇴화](#2-극단퇴화) | 경계값과 퇴화 입력을 일부러 넣는다 | 반올림 규칙, 0 나누기, 미초기화 |
| [3. 불변량](#3-불변량) | 값이 아니라 구조적 성질을 확인한다 | 공유·소유권, 지연 계산 |
| [4. 알려진 정답](#4-알려진-정답) | 답을 미리 아는 문제를 푼다 | float 정밀도 붕괴 |
| [5. 왕복](#5-왕복) | 넣었다 되돌려 원래 값이 나오는지 본다 | 좌표 규약, 채널 순서 |
| [6. 차원·단위](#6-차원단위) | 순서·단위가 뒤집힌 쌍을 찾는다 | `(y,x)` 대 `(x,y)` |

## 1. 두 경로 대조

> **같은 일을 두 가지 방법으로 시키고 답이 같은지 본다.** 정답을 몰라도 됩니다.
> 두 답이 다르면 적어도 하나는 틀렸고, 그 사실만으로 조사가 시작됩니다.

모델이 쓴 코드를 검토할 때 가장 자주 쓰게 되는 검사입니다. "이게 맞나?" 는 판단이
필요하지만 "이 둘이 같나?" 는 실행만 하면 됩니다.

### 8비트 평균 — 같아 보이는 형태가 다르게 행동합니다

`uchar` 영상 두 장의 평균입니다. OpenCV 로 네 가지를 쓰고, 대조군으로 순수 C++ 와
`add` 단독을 더해 **여섯 가지**를 나란히 쟀습니다.

```cpp
cv::Mat e1 = (a + b) / 2;                       // 한 줄
cv::Mat sum; cv::add(a, b, sum);
cv::Mat e2 = sum / 2;                           // 두 줄로 나눠 쓴 같은 식
cv::Mat e3 = a / 2 + b / 2;                     // 각각 나눈 뒤 더하기
cv::Mat e4; cv::addWeighted(a, 0.5, b, 0.5, 0.0, e4);
```

| (A, B) | 참값 | `(a+b)/2` | `add` 후 `/2` | `a/2+b/2` | `addWeighted` | 순수 C++ | `add` 단독 |
|---|---|---|---|---|---|---|---|
| (200, 100) | 150 | **150** | **128** | 150 | 150 | 150 | 255 |
| (201, 101) | 151 | **151** | **128** | 151 | 151 | 151 | 255 |
| (255, 255) | 255 | **255** | **128** | 255 | 255 | 255 | 255 |
| (7, 8) | 7.5 | 8 | 8 | 8 | 8 | **7** | 15 |

**`cv::add` 후 `/2` 는 입력과 무관하게 128 을 줍니다.** `add` 가 CV_8U 에서 255 로
포화한 뒤 나누니 언제나 127.5 → 128 입니다. 크래시하지 않고, 영상은 그럴싸하게 나옵니다.

한 줄로 쓴 `(a+b)/2` 는 맞습니다. `MatExpr` 이 이 식을 `addWeighted` 로 접어서 중간
포화가 없기 때문입니다. 그러니 교훈은 "이 형태를 써라" 가 아닙니다 — 그건 구현
세부이고 버전마다 다를 수 있습니다. 교훈은 이쪽입니다.

> **같아 보이는 두 형태가 다르게 행동한다.** 한 줄을 두 줄로 "리팩터링" 하는 순간 값이
> 바뀝니다. 그리고 그 리팩터링은 리뷰에서 절대 안 걸립니다.

### ROI 에서 `step` 을 `cols` 로 가정하기

6×5 행렬에 `y*10+x` 를 채우고 `Rect(1,1,3,3)` 로 ROI 를 잡은 뒤, 같은 화소를 네 가지
경로로 읽었습니다.

```
full: cols=5  step=5  isContinuous=1
roi : cols=3  step=5  isContinuous=0      ← step 이 cols 가 아니다
```

| 접근 | 값 |
|---|---|
| `roi.at<uchar>(1,1)` (참값) | 22 |
| `roi.ptr<uchar>()[1*roi.cols + 1]` | **20** |
| `roi.ptr<uchar>()[1*roi.step + 1]` | 22 |
| `roi.ptr<uchar>(1)[1]` | 22 |

네 경로 중 하나만 다릅니다. **틀린 화소를 읽고 크래시하지 않습니다** — 20 도 그럴싸한
값이니까요. 정답을 몰라도 "넷 중 하나가 다르다" 는 것만으로 버그를 찾습니다.

> 실무 규칙: `ptr<T>(y)[x]` 를 쓰면 항상 맞습니다.

### 같은 데이터를 다른 타입으로 읽기

```cpp
cv::Mat f(1, 4, CV_32F);           // 1.0, 2.0, 3.0, 4.0 을 넣었다
f.at<uchar>(0, i);                 // uchar 로 읽으면?
```

```
0 0 128 63
```

`1.0f` 의 리틀엔디언 바이트 `00 00 80 3F` 입니다. **컴파일되고 크래시하지 않습니다.**
`at<T>` 는 Release 에서 타입을 검사하지 않습니다. 올바른 타입으로 읽은 값과 나란히
놓지 않으면 이걸 알아챌 방법이 없습니다.

### Release 와 Debug 를 따로 재기

2000×2000 CV_8U 전체 합, 5회 중 최소:

| 접근 | Release `/O2` | Debug `/Od` |
|---|---|---|
| `at<uchar>(y,x)` | 0.74 ms | **18.03 ms** |
| `ptr<uchar>(y)[x]` | 0.48 ms | 2.07 ms |
| `data[i]` 연속 가정 | 2.39 ms | 36.49 ms |
| `cv::sum` | **0.09 ms** | 9.05 ms |
| **at / ptr 비** | **1.52×** | **8.73×** |

두 열을 나란히 놓지 않았다면 통설을 그대로 믿었을 겁니다. 세 가지가 다릅니다.

**첫째, Release 에서 차이는 1.5배뿐입니다.** 통설의 10\~50배는 Debug 값입니다 —
`at<>` 자체가 Release 대비 24배 느려집니다(경계 검사). `at<>` 루프를 포인터로 고쳐
쓰는 리팩터링은 Release 빌드에서 거의 이득이 없습니다.

**둘째, `data[i]` 로 평평하게 도는 것이 오히려 느렸습니다** (0.31×). "연속이니까 한
루프로 돌면 빠르다" 가 이 컴파일러에서는 틀렸습니다. 행 단위 루프는 벡터화되고
`total()` 단일 루프는 안 된 것으로 보입니다.

**셋째, 진짜 이득은 OpenCV 함수입니다** — `cv::sum` 이 8.09배. 손으로 루프를 고치는
것보다 이쪽이 훨씬 큽니다.

> ⚠️ Debug 에서 `cv::sum` 이 9.05 ms 로 Release 의 **100배**입니다. 디버그 DLL 은
> 벡터화 경로가 죽습니다. **Debug 에서 잰 시간으로 최적화 결정을 내리면 안 됩니다.**
> 위 표의 두 열은 순위조차 다릅니다.

그리고 배율이 가장 큰 항목은 접근 방식이 아니라 이것이었습니다.

| 500행 루프 | 시간 |
|---|---|
| `m.row(y)` (헤더만) | 0.01 ms |
| `m.row(y).clone()` | 0.37 ms |
| 배율 | **38.5×** |

## 2. 극단·퇴화

> **경계값과 퇴화 입력을 일부러 넣는다.** 평범한 입력에서는 모든 구현이 맞습니다.
> 갈리는 곳은 언제나 끝입니다 — 최댓값, 0, 정확히 절반, 홀수 크기, 빈 것.

모델은 "전형적인" 입력을 가정하고 코드를 씁니다. 그래서 이 검사가 잘 듭니다.

### 최댓값을 넣으면 포화가 드러납니다

위 §1 표의 `(255, 255)` 행입니다. 참값이 255 인데 `add` 후 `/2` 는 **128** 을 줍니다.
(200,100) 만 봤다면 "128, 뭔가 좀 이상한데" 였겠지만, (255,255) 에서도 128 이 나오는
순간 **입력과 무관하게 128** 이라는 게 드러납니다. 원인이 특정됩니다.

### 정확히 절반에서 반올림 규칙이 갈립니다

| 입력 | 0.4 | **0.5** | 0.6 | **1.5** | **2.5** | **254.5** | 300.0 | −1.0 |
|---|---|---|---|---|---|---|---|---|
| `saturate_cast<uchar>` | 0 | **0** | 1 | **2** | **2** | **254** | 255 | 0 |
| `(uchar)` C 스타일 | 0 | 0 | **0** | **1** | 2 | — | — | — |

`0.5 → 0`, `1.5 → 2`, `2.5 → 2`, `254.5 → 254`. **짝수로 붙습니다**(round-half-to-even).
흔히 믿는 "0.5 는 올림" 이 아닙니다.

그리고 C 스타일 캐스트는 반올림이 아니라 **절단**입니다. `0.6 → 0`, `1.5 → 1`.
같은 자리에서 둘을 섞어 쓰면 1 레벨씩 어긋나고, 그건 영상에서 안 보입니다.
`0.4` 와 `0.6` 만 넣어봤다면 두 행이 같아 보였을 겁니다.

### 0 으로 나누면 타입에 따라 다릅니다

| | 입력 | 결과 |
|---|---|---|
| `CV_32F` `a / b` | `[1,2,3] / [1,0,3]` | `1, inf, 1` |
| `CV_8U` `cv::divide` | 같음 | `1, 0, 1` |

float 는 `inf` 를 내보내고 정수는 0 으로 막습니다. **같은 코드가 타입에 따라 다르게
행동합니다.** 뒤에 `inf` 가 섞인 배열이 통계로 들어가면 결과 전체가 `nan` 이 됩니다.

### 홀수 폭까지 훑기 — 클로드의 주장이 여기서 깨졌습니다

`step != cols` 가 정렬 패딩 때문이라는 게 클로드가 든 예시 중 하나였습니다. 폭을
훑어봤습니다.

| 폭 | `step` |
|---|---|
| 640 | 640 |
| 641 | 641 |
| 643 | 643 |
| 1000 | 1000 |

**홀수 폭에서도 패딩이 없습니다.** `step != cols` 의 출처는 ROI(와 외부 버퍼)이고,
"정렬 때문에 붙는다" 가 아닙니다. 짝수 폭만 봤다면 아무것도 알 수 없었습니다.

### 아무것도 안 넣은 것도 입력입니다

```cpp
cv::Mat m(8, 8, CV_8U);          // zeros 가 아니다
```

200회 만들어 `countNonZero` 를 재니 **200회 전부** 0 이 아닌 값이 들어 있었습니다.

> ⚠️ 반대로 0 이 나와도 보장이 아닙니다. 할당자가 준 메모리에 달렸고, 이건 정의되지
> 않은 동작입니다. 이 표는 "이렇게 된다" 가 아니라 "이 실행에서 이렇게 나왔다" 입니다.
> **UB 를 관측한 결과를 규칙처럼 쓰면 안 됩니다.**

## 3. 불변량

> **값이 아니라 구조적 성질을 확인한다.** 값은 우연히 맞을 수 있지만 성질은
> 아닙니다. "이 둘이 메모리를 공유하는가", "이 객체가 데이터를 소유하는가" 는
> 출력이 그럴싸한지와 무관하게 답이 정해집니다.

조용히 틀리는 코드에 가장 강한 검사입니다. 값을 보는 검사는 운이 좋으면 통과하지만,
불변량은 운이 개입하지 않습니다.

### 공유 여부는 값이 아니라 포인터로 판정합니다

`cv::Mat` 은 참조 카운트라 대입이 데이터를 복사하지 않습니다. 어디까지 그런지
`base.at<uchar>(1,1) = 77` 을 실행한 뒤 확인했습니다.

| 만든 방법 | 값 | `data` 공유 |
|---|---|---|
| `cv::Mat b = base;` | **77** | 예 |
| `base(cv::Rect(...))` | **77** | 예 |
| `base.reshape(1, 2)` | **77** | 예 |
| `base.clone()` | 0 | 아니오 |
| `base.convertTo(dst, CV_8U)` (같은 타입) | 0 | 아니오 |

`reshape` 도 공유합니다 — 헤더만 바꾸니 당연하지만 이름이 그렇게 안 읽힙니다.
`convertTo` 는 타입이 같아도 복사합니다.

> **판별법은 값을 비교하는 게 아니라 포인터를 비교하는 것입니다:** `a.data == b.data`.
> 값 비교는 "아직 안 건드려서 같아 보이는" 경우를 통과시킵니다.

### 소유권 — `m.u == nullptr` 이 표식입니다

여기가 클로드가 든 네 번째 예시가 깨진 곳입니다. Eigen 의 유명한 dangling 함정이
OpenCV 에도 있다고 했는데, 죽은 지역변수를 참조하는 `MatExpr` 을 평가해도 **정상값
7 이 나왔습니다.** `cv::Mat` 이 참조 카운트라서 `MatExpr` 이 들고 있는 얕은 복사가
데이터를 살려둡니다.

진짜 dangling 은 **외부 버퍼를 감쌀 때**입니다.

```cpp
cv::Mat wrap() {
    std::vector<float> v(16, 5.f);
    return cv::Mat(4, 4, CV_32F, v.data());   // v 가 여기서 죽는다
}
```

이 실행에서는 5 가 나왔습니다 — 해제된 스택이 아직 덮이지 않았을 뿐입니다. **값을
봤다면 "정상" 으로 통과시켰을 코드입니다.** 판별은 값이 아니라 소유권입니다.

> **`m.u == nullptr` 이면 그 `Mat` 은 데이터를 소유하지 않습니다.** 위 `wrap()` 의
> 결과가 그렇습니다. 함수 경계를 넘는 `Mat` 은 이걸 확인하세요.

### 타입도 불변량입니다 — `auto` 가 `Mat` 이 아닐 때

```cpp
cv::Mat a = ones*3, b = ones*4;
auto e = a + b;            // 이것은 Mat 이 아니다
a.setTo(100);              // 나중에 a 를 고친다
cv::Mat r = e;             // 여기서 계산된다
```

`decltype(e)` 가 `cv::Mat` 인지 확인하면 **false** 입니다. `cv::MatExpr` 이고, 아직
계산되지 않았습니다. 그래서

| | 값 |
|---|---|
| `a+b` 를 즉시 계산했다면 | 7 |
| **실측** | **104** |

`auto` 하나가 "값을 저장" 에서 "식을 저장" 으로 바뀌고, 나중의 수정이 결과에
들어갑니다. `static_assert(std::is_same_v<decltype(e), cv::Mat>)` 한 줄이 이걸
컴파일 타임에 잡습니다.

## 4. 알려진 정답

> **답을 미리 아는 문제를 푼다.** 구현이 맞는지 판단할 수 없을 때, 판단이 필요 없는
> 입력을 만들어 넣습니다.

수치 코드에서 특히 강합니다. 모델이 쓴 수치 코드는 "돌아가는데 답이 조금 다른"
상태가 되기 쉬운데, 정답을 알면 "조금" 이 몇 자리인지 셀 수 있습니다.

### 0.1 을 N 번 더하면 얼마인가

| N | float | double | 상대오차 |
|---|---|---|---|
| 1,000 | 99.999046 | 100.000000 | 9.54e-6 |
| 100,000 | 9998.5566 | 10000.0000 | 1.44e-4 |
| 10,000,000 | **1087937.0** | 1000000.0 | **8.79e-2** |

천만 번에서 8.8% 틀립니다. 108만 대 100만입니다. 정답이 `0.1 × N` 이라는 걸 알기
때문에 이 표가 만들어집니다.

### 답이 전부 1 인 최소자승

기하 코드에서 더 중요한 건 이쪽입니다. 6×6 Hilbert 행렬(악명 높은 나쁜 조건수)로
최소자승을 풀었습니다. **답이 전부 1 이 되도록 우변을 잡고** `cv::solve(..., DECOMP_SVD)`:

| 정밀도 | 해의 최대오차 |
|---|---|
| `CV_32F` | **1.71e-1** |
| `CV_64F` | 5.83e-11 |

float 로 풀면 1 이어야 할 답이 0.83 으로 나옵니다. **9 자리 차이**입니다.
[8편]({{< ref "/posts/triangulation" >}})에서 조건수가 답의 불확실성을 정한다고 했는데,
정밀도가 부족하면 그 불확실성이 잡음이 아니라 **구현에서** 나옵니다. 삼각측량·PnP·
번들조정 같은 것을 `CV_32F` 로 세우면 안 되는 이유입니다.

정답을 몰랐다면 `0.83` 은 그냥 "대충 맞는 값" 입니다.

## 5. 왕복

> **넣었다 되돌려 원래 값이 나오는지 본다.** 정변환과 역변환을 아는 것으로 충분하고,
> 중간 결과가 맞는지는 몰라도 됩니다.

좌표 규약과 포맷 변환처럼 **규약을 잘못 잡아도 그럴싸한 결과가 나오는** 곳에 씁니다.

### `resize` 의 화소 중심 규약

`[0,1,2,...,7]` 을 `INTER_LINEAR` 로 두 배 확대했습니다.

```
0.00 0.25 0.75 1.25 1.75 2.25 2.75 3.25 3.75 4.25 4.75 5.25 5.75 6.25 6.75 7.00
```

두 가설이 있습니다. 화소 중심이 정수라면 `i=1` 에서 0.50 이 나와야 하고, 화소 중심이
반 화소 어긋나 있다면 0.25 가 나와야 합니다. **실측 0.25** 이므로 쓰이는 대응은

\[
\text{src} = (i + 0.5)\,s - 0.5
\]

입니다. 양 끝(0.00, 7.00)은 정의역 밖이라 클램프됩니다.

### 왕복시키면 규약 오차가 드러납니다

`warpAffine` **항등변환은 최대 오차 0.00 으로 정확합니다.** 그런데 0.5 화소 이동을
오른쪽으로 한 번, 왼쪽으로 한 번 하면

> **최대 오차 0.50** (원값 범위 0\~7 이니 전체의 7%)

선형보간이 두 번 걸리면서 저역통과가 두 번 들어갑니다. 파이프라인에서 좌표 규약을
한 번 잘못 잡으면 이만큼이 매 단계 쌓입니다. 그리고 결과 영상은 **조금 흐려진 정상
영상**으로 보입니다 — 한 번만 변환해서는 절대 안 보입니다.

### 파일로 썼다 읽기

`Scalar(0,0,255)` 로 만든 빨강을 PNG 로 쓰고 다시 읽으면 `(0,0,255)`,
`COLOR_BGR2RGB` 를 거치면 `(255,0,0)` 입니다. **`imread` 는 BGR 을 줍니다.**
학습 모델은 대개 RGB 를 기대하므로 여기서 채널이 뒤집히면 **정확도만 조금 떨어진
정상 모델**로 보입니다. 왕복시켜 놓고 채널을 직접 찍어보는 것이 유일한 확인법입니다.

## 6. 차원·단위

> **순서와 단위가 뒤집힌 쌍을 찾는다.** 같은 두 숫자를 다른 순서로 받는 API 가
> 나란히 있으면, 그 자리는 반드시 한 번 틀립니다.

```cpp
cv::Mat m = cv::Mat::zeros(3, 6, CV_8U);   // rows=3, cols=6
m.at<uchar>(1, 4) = 99;                    // (행, 열)
```

| 접근 | 값 |
|---|---|
| `m.at<uchar>(1, 4)` | 99 |
| `m.at<uchar>(cv::Point(4, 1))` | 99 |
| `m.size() == cv::Size(6, 3)` | true |

`at` 은 `(y, x)`, `Point` 는 `(x, y)`, `Mat` 생성자는 `(rows, cols)`, `Size` 는
`(width, height)` 입니다. **두 쌍이 서로 뒤집혀 있는 것**이 사고의 근원입니다.

> 🚨 **정사각 영상으로 테스트하면 이 버그가 전부 통과합니다.** 그래서 이 검사는
> "직사각형으로 테스트한다" 라는 한 줄로 요약됩니다. 640×480 을 쓰세요.

## 그래서 무엇을 위임하나

여섯 검사를 관통하는 기준이 하나 있습니다. **틀렸을 때 컴파일러가 알려주는가.**

| 위임해도 되는 것 | 직접 판정해야 하는 것 |
|---|---|
| 문법, API 이름, CMake 주문 | 소유권과 수명 |
| 반복문·boilerplate | 타입과 값 범위 |
| 알고리즘 골격 | 메모리 배치(`step`) |
| 최적화 아이디어 | 좌표 규약 |

오른쪽 열이 전부 **크래시하지 않는** 범주라는 것이 핵심입니다. 왼쪽 열은 틀리면
컴파일러가 알려주니 위임해도 안전합니다. 그리고 오른쪽 열의 네 항목이 위 여섯 검사의
1·2·3·5·6 번이 겨냥하는 바로 그 지점입니다.

## 보너스 — 이 글을 쓰다 실제로 걸린 것

여섯 검사에 안 들어가는, 그냥 빌드가 잡아준 것도 하나 적어둡니다. 첫 빌드가 이렇게
실패했습니다.

```
error C4430: 형식 지정자가 없습니다. int로 가정합니다.
error C2001: 상수에 줄 바꿈 문자가 있습니다
```

원인은 인코딩입니다. MSVC 는 **BOM 없는 UTF-8 소스를 시스템 코드페이지(CP949)로
읽습니다.** 일부 한글의 둘째 바이트가 `0x5C`(`\`) 라서 문자열 리터럴이 닫히지 않고,
그 결과 완전히 엉뚱한 자리에서 문법 오류가 납니다.

```
cl /utf-8 ...
```

한글 주석을 쓰는 사람에게는 이게 목록의 0번입니다. 그리고 이건 **싼 버그**입니다 —
빌드가 멈추니까요.

## 정리

- 🚨 **클로드가 든 예시 넷이 전부 틀렸다.** `(a+b)/2` 는 127 이 아니라 150 이고
  (`MatExpr` 이 `addWeighted` 로 접는다), `step != cols` 는 정렬 패딩이 아니라 ROI 에서
  오고, `at<>` 는 10\~50배가 아니라 Release 에서 1.52배 느리며, OpenCV `MatExpr` 은
  `cv::Mat` 이 참조 카운트라 Eigen 처럼 dangling 하지 않는다. **넷을 잡아낸 것은 지식이
  아니라 검사였다** — 두 경로 대조 둘, 극단 하나, 불변량 하나
- **두 경로 대조** — `add` 후 `/2` 는 입력과 무관하게 **128**, 한 줄로 쓴 같은 식은 맞다.
  ROI 에서 `ptr()[y*cols+x]` 는 22 대신 20 을 읽는다. Release 와 Debug 는 **순위조차
  다르다**(`cv::sum` 이 Debug 에서 100배 느리고, `data[i]` 평평 루프는 Release 에서
  `at<>` 보다 **더 느렸다** 0.31×). 배율 최대는 루프 안 `clone` **38.5×**
- **극단·퇴화** — (255,255) 가 포화를 드러내고, `saturate_cast` 는
  **round-half-to-even**(`0.5→0`, `1.5→2`, `2.5→2`), 0 나누기는 float `inf` / 정수 `0`,
  폭 640·641·643·1000 전부 패딩 없음, 초기화 안 한 `Mat` 은 200/200 회 쓰레기(단 UB)
- **불변량** — 공유 판정은 값이 아니라 `a.data == b.data`(`reshape` 공유, `convertTo`
  복사). 소유권 표식은 **`m.u == nullptr`**. `auto e = a + b` 는 `Mat` 이 아니라
  `MatExpr` 이고 지연 계산이라 결과가 7 이 아니라 **104**
- **알려진 정답** — 0.1 을 천만 번 더하면 **8.8% 틀리고**, 6×6 Hilbert 최소자승을
  `CV_32F` 로 풀면 답이 1 대신 0.83 이다(`CV_64F` 는 5.8e-11). 기하 추정을 float 로
  세우면 안 된다
- **왕복** — `resize` 는 \((i+0.5)s - 0.5\) 를 쓴다. `warpAffine` 항등변환은 오차 0.00
  이지만 **0.5 px 왕복은 최대 0.50 을 잃는다**(범위의 7%) — 결과는 살짝 흐린 정상
  영상이다. `imread` 는 BGR 을 준다
- **차원·단위** — `at(y,x)` / `Point(x,y)` / `Mat(rows,cols)` / `Size(w,h)` 가 서로
  뒤집혀 있고, **정사각 영상으로 테스트하면 전부 통과한다**
- 목록은 프로젝트마다 바뀐다. 전이되는 것은 **검사 여섯 종류**다

> 것을 쓰면 클로드가 틀린 넷을 한 번 더 반복하는 것이기 때문입니다. 열 우선 저장과

> 형태가 다르게 행동한다" 로 적었습니다. 다른 버전에서 다르게 나오면 알려주세요.

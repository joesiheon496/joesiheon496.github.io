> 🔎 **조사 글**: 표준 문서 요약이 아니라, OCR/비전 인식 시스템을 만드는 사람 관점에서
> 체크디지트 규칙들을 해부한 것이다. **검출률·정정 후보 표는 전부 제가 직접 전수 계산한
> 값**이고, 재현 코드를 부록에 붙였다. 출처는 글 끝에 모았다.

## 어디에 쓰는가

문서에서 카드번호를 읽든, 검사 라인에서 제품 코드를 읽든, 등록 창구에서 차대번호를
읽든 — 현장의 이미지는 험하다. 긁히고, 반사되고, 잉크가 번진다. 아무리 좋은 OCR 도
이런 입력에서 문자 하나쯤은 틀리고, 숫자열에서 문자 하나가 틀리면 **완전히 다른
번호**가 된다. 틀렸다는 표시도 없이.

그래서 세상의 중요한 번호들은 애초에 **오류 검출용 자리 하나**를 품고 설계돼 있다.
카드번호의 마지막 자리, 바코드의 마지막 자리, ISBN 의 마지막 자리, 차대번호(VIN)의
9번째 자리 — 전부 나머지 자리들로부터 **계산되는** 숫자다. 인식 시스템의 마지막
관문은 늘 이 검사고, 잘 쓰면 검증을 넘어 **정정**까지 된다.

## 공통 뼈대 — 가중합 mod N

겉모습은 제각각이지만 뼈대는 하나다.

```
(자리₁값 × 가중치₁ + 자리₂값 × 가중치₂ + …)  mod N  =  약속된 값
```

한 자리가 다른 값으로 바뀌면 합이 `(값 차이) × 그 자리 가중치` 만큼 변한다.
그러니 규칙의 검출력은 딱 두 조건에 달려 있다.

1. **가중치가 mod N 에서 0 이 아니어야 한다** — 0 이면 그 자리는 아예 검사 대상이 아니다
2. **서로 다른 두 값의 차이가 N 의 배수가 아니어야 한다** — 배수면 그 둘 사이의 오독은 투명인간이다

숫자 0~9 만 쓰는 규칙은 N=10 또는 11 에서 조건 2 가 거저 얻어진다(한 자리 차이는
최대 9). 문자까지 들어오면 값 배정표가 승부처가 된다. 이제 실제 규칙 네 개를 이
잣대로 해부한다. 아래의 모든 성질은 부록 코드로 전수 확인한 것이다.

## 규칙 1 — Luhn (mod 10) : 카드번호

신용카드 번호의 마지막 자리. 1954년 IBM 의 Hans Peter Luhn 이 특허 낸 규칙이다.
오른쪽에서부터 짝수 번째 자리를 2배 하고, 9를 넘으면 9를 뺀 뒤(=자릿수 합),
전체 합이 10 의 배수가 되어야 한다.

- 검증 예: `79927398713` → 합 70 → **통과** (교과서 예제, 직접 확인)
- **단일 치환: 100% 검출.** "2배 후 자릿수 합" 이 0~9 를 서로 다른 값으로 보내기 때문
- **인접 전위(두 자리 뒤바뀜): 딱 한 쌍을 놓친다 — `09 ↔ 90`.** 전수 확인 결과 90가지 순서쌍 중 이 2가지만 투명하다

카드번호 OCR 에서 전위 오류는 드물지만(문자 순서가 바뀌는 건 사람 손 입력의 오류
패턴이다), 단일 치환 100% 라는 성질이 OCR 검증 게이트로는 충분히 유효하다.

## 규칙 2 — EAN-13 (mod 10, 가중치 1·3) : 바코드/제품 코드

상품 바코드 아래 인쇄된 13자리. 스캐너가 못 읽어 사람이 치거나 OCR 로 읽는 일이
많아서, 검사 라인의 문자 인식에도 자주 등장한다. 왼쪽부터 가중치 1, 3 을 번갈아
곱해 합이 10 의 배수여야 한다.

- 검증 예: `4006381333931` → **통과** (직접 확인)
- **단일 치환: 100% 검출.** 1 도 3 도 mod 10 에서 가역이라 조건 1 을 만족
- **인접 전위: 값 차이가 5 인 쌍을 놓친다.** `0↔5, 1↔6, 2↔7, 3↔8, 4↔9` — 가중치 차이가 2 라서 `2×5=10 ≡ 0` 이 되기 때문. 전수 확인 결과 90가지 중 10가지가 투명하다

Luhn 보다 전위에 약하다. 대신 계산이 단순해서 하드웨어 스캐너에 심기 좋았다.

## 규칙 3 — ISBN-10 (mod 11) : 소수 모듈러스의 힘

책 뒤의 10자리. 왼쪽부터 가중치 10, 9, …, 1 을 곱해 합이 11 의 배수여야 한다.
나머지가 10 이 되는 자리는 숫자가 없으므로 **문자 X 를 도입**했다.

- 검증 예: `0-306-40615-2` → **통과** (직접 확인)
- **단일 치환: 100% 검출. 인접 전위: 100% 검출.** 네 규칙 중 유일한 만점이다

만점의 비결은 모듈러스가 **소수** 라는 것이다. 11 이 소수라 0 이 아닌 어떤 가중치도,
어떤 값 차이(±1~±9)도 11 과 서로소다 — 조건 1, 2 가 자동으로 성립한다. mod 10 은
합성수라 2 나 5 가 낀 조합에서 반드시 구멍이 난다(위의 EAN 전위 구멍이 정확히 그것).

재미있는 사실: 2007년 ISBN 이 13자리로 바뀌면서 계산법이 **EAN-13 방식으로 넘어갔다.**
바코드 인프라와의 호환을 얻는 대가로, 오류 검출력은 오히려 후퇴한 것이다.
표준 설계에서도 공짜 점심은 없다.

## 규칙 4 — VIN 차대번호 (mod 11) : OCR 을 미리 고려한 설계

차량 등록·검사 시스템이 읽는 17자리 차대번호. 9번째 자리가 체크디지트다.
문자를 값으로 음역하고(A=1, B=2, …, 단 몇 개 예외), 자리별 가중치
`8 7 6 5 4 3 2 10 0 9 8 7 6 5 4 3 2` 를 곱해 mod 11 — 나머지 10 은 ISBN 처럼
**X 로 표기**한다.

- 검증 예: `1M8GDM9AXKP042788` → 9번째 자리 X, 계산값도 **X** (직접 확인)
- 표준이 **I, O, Q 를 아예 금지**했다. 1, 0 과 가장 헷갈리는 문자 셋을 번호 체계에서 빼 버린 것 — 표준 설계자가 수기·OCR 오독을 미리 반영한 드문 사례다
- 대신 문자 음역에 겹침이 있다. 음역표가 26개 문자를 1~9 에 욱여넣으므로 같은 값을 받는 문자·숫자 무리가 생긴다. 전수 계산한 무리는 다음과 같다:

| 값 | 같은 값 (서로 오독해도 못 잡음) |
|---|---|
| 1 | A, J, 1 |
| 2 | B, K, S, 2 |
| 3 | C, L, T, 3 |
| 4 | D, M, U, 4 |
| 5 | E, N, V, 5 |
| 6 | F, W, 6 |
| 7 | G, P, X, 7 |
| 8 | H, Y, 8 |
| 9 | R, Z, 9 |

이 표를 OCR 의 눈으로 보면 다행히 관대하다. 전형적 혼동쌍인 8↔B (8 vs 2),
5↔S (5 vs 2), 2↔Z (2 vs 9) 는 **전부 다른 값이라 잡힌다.** 진짜 헷갈리는
0↔O, 1↔I 는 금지로 원천 차단됐고. 같은 무리 안의 쌍(A↔J, H↔Y 등)은 시각적으로
멀어서 실전 오독이 드물다. 설계가 잘 짜인 셈이다.

## "나머지 10" 을 다루는 세 가지 태도

mod 11 계열엔 공통의 고민이 있다. 체크 값이 0~10 의 11가지인데 숫자는 10개뿐이다.
표준들이 갈라지는 지점이고, OCR 검증기 구현에도 그대로 영향을 준다.

| 태도 | 예 | 결과 |
|---|---|---|
| 문자 X 도입 | ISBN-10, VIN | 정보 손실 없음. 검증력 유지. 다만 "숫자 자리에 X" 라는 예외를 인식기와 검증기가 다 알아야 한다 |
| 그런 번호를 회피 | 일부 채번 규칙 | 발급 단계에서 나머지 10 이 나오는 번호를 안 만든다. 무작위 번호의 약 1/11 을 버리는 비용 |
| 10 을 0 으로 접기 | 일부 산업 코드 | 표기는 깔끔하지만 **체크 값 0 이 두 잉여류(0, 10)를 커버해 그 코드들의 검증력이 약해진다** |

세 번째가 은근한 함정이다. 접기를 쓰는 규칙에서 체크디지트가 0 인 코드는, 오독이
나머지 0 경로와 10 경로 어느 쪽으로 떨어져도 통과시킨다. 검증기를 짤 때 이 분기를
빼먹으면 두 방향으로 사고가 난다 — 접기를 모르면 멀쩡한 번호의 약 9%(≈1/11)를
불합격시키고, 접기만 알고 약화를 모르면 체크 0 코드의 오독 통과율을 과소평가한다.

## 검증을 넘어 정정으로 — OCR 파이프라인에서 쓰는 법

체크디지트의 진짜 힘은 불합격 판정이 아니라 정정이다. 실무 파이프라인은 대개
이렇게 겹겹이 쌓는다.

1. **포맷 사전(prior)이 1차** — 자리별로 올 수 있는 문자 집합을 인식 단계에서 제한한다. 숫자 자리에서 `O` 가 나오면 그건 애초에 `0` 이다. 0↔O, 1↔I, 5↔S, 8↔B, 2↔Z 같은 숫자-문자 혼동은 체크디지트까지 갈 필요도 없이 여기서 죽는다
2. **체크디지트가 2차 게이트** — 통과 못 하면 그 판독은 폐기하거나 다음 단계로
3. **최저 confidence 문자 역산** — OCR 은 문자별 확신도를 주므로, 검증 실패 시 가장 자신 없는 자리 하나를 미지수로 두고 체크섬을 만족하는 값을 역산한다. mod 11 소수 계열은 가중치가 가역이라 **숫자 자리 미지수는 후보가 정확히 1개**로 떨어진다 (ISBN-10 기준, 직접 확인). mod 10 계열이나 문자 음역이 겹치는 규칙(VIN)은 후보가 2~4개 — confidence 순위와 결합해 고른다
4. **다중 프레임/다중 뷰 투표** — 영상이면 수십 프레임이 같은 번호를 본다. 문자 단위로 투표시키고 체크섬을 통과하는 조합을 채택한다
5. **등록부 대조** — 발급된 번호 목록(카드 BIN 테이블, 도서 DB, 차량 등록 DB…)이 있다면 최종 대조. 체크섬이 필터라면 이것은 증명에 가깝다

주의할 것 하나: **통과 ≠ 정답**이다. 두 자리가 동시에 틀리면 우연히 합이 맞을 수
있고(대략 1/N 확률), 위에서 본 각 규칙의 구멍(같은 값 무리, 전위 취약쌍)도 있다.
체크디지트는 오독의 대부분을 걸러 주는 싸고 강력한 필터지, 무결성 증명이 아니다.

## 남는 교훈

네 규칙을 한 줄씩으로 접으면:

| 규칙 | mod | 단일 치환 | 인접 전위 | 특징 |
|---|---|---|---|---|
| Luhn | 10 | 100% | 09↔90 만 놓침 | 2배-자릿수합 트릭 |
| EAN-13 | 10 | 100% | 차이 5 쌍 놓침 | 단순함 우선 |
| ISBN-10 | 11 | **100%** | **100%** | 소수 모듈러스 + X |
| VIN | 11 | 음역 겹침 제외 100% | 가중치 덕에 대부분 | I/O/Q 금지 — OCR 친화 설계 |

그리고 비전 시스템 설계자에게 남는 일반 교훈: **출력 도메인에 구조가 있으면, 그
구조를 후처리가 아니라 디코딩 제약으로 밀어 넣어라.** 인식 모델의 정확도를 1%p
올리는 것보다 도메인 규칙 하나를 파이프라인에 넣는 것이 시스템 오류율을 훨씬 크게
깎는 경우가 많다. 세상의 번호들이 이미 규칙을 품고 태어난다는 것 — 그걸 쓰지 않을
이유가 없다.

## 부록: 전수 검증 코드

본문의 모든 성질(각 규칙의 검증 예, 치환·전위 검출률, VIN 음역 무리)은 아래 코드의
출력이다.

```python
from collections import defaultdict

# --- Luhn (mod 10) ---
def luhn_sum(num):
    s = 0
    for i, c in enumerate(reversed(num)):
        d = int(c)
        if i % 2 == 1:
            d *= 2
            if d > 9:
                d -= 9
        s += d
    return s % 10

assert luhn_sum("79927398713") == 0          # 교과서 예제

# 인접 전위 중 놓치는 쌍 — (0,9) 와 (9,0) 뿐
missed = [(a, b) for a in range(10) for b in range(10) if a != b
          and luhn_sum(f"{a}{b}0000000") == luhn_sum(f"{b}{a}0000000")]
print("Luhn 전위 구멍:", missed)

# --- EAN-13 (mod 10, 가중치 1·3) ---
def ean13_ok(num):
    return sum(int(c) * (3 if i % 2 else 1) for i, c in enumerate(num)) % 10 == 0

assert ean13_ok("4006381333931")
# 전위 구멍: 가중치 차 2 → 2×(값 차이) ≡ 0 (mod 10) ⇔ 값 차이 = 5
print("EAN 전위 구멍:", [(a, b) for a in range(10) for b in range(10)
                        if a != b and 2 * (a - b) % 10 == 0])

# --- ISBN-10 (mod 11) ---
def isbn10_ok(isbn):
    return sum((10 - i) * (10 if c == 'X' else int(c))
               for i, c in enumerate(isbn)) % 11 == 0

assert isbn10_ok("0306406152")
# 단일 치환·인접 전위 전수: 구멍 0개 (소수 모듈러스)
subs = [(p, a, b) for p in range(10) for a in range(10) for b in range(10)
        if a != b and (10 - p) * (a - b) % 11 == 0]
trans = [(p, a, b) for p in range(9) for a in range(10) for b in range(10)
         if a != b and 1 * (a - b) % 11 == 0]   # 인접 가중치 차이는 항상 1
print("ISBN-10 구멍:", len(subs), len(trans))

# --- VIN (mod 11) ---
VALS = {}
for grp, start in [("ABCDEFGH", 1), ("JKLMN", 1), ("P", 7), ("R", 9),
                   ("STUVWXYZ", 2)]:
    for k, ch in enumerate(grp):
        VALS[ch] = start + k
for d in "0123456789":
    VALS[d] = int(d)
W = [8, 7, 6, 5, 4, 3, 2, 10, 0, 9, 8, 7, 6, 5, 4, 3, 2]

def vin_check(vin):
    r = sum(VALS[c] * w for c, w in zip(vin, W)) % 11
    return 'X' if r == 10 else str(r)

assert vin_check("1M8GDM9AXKP042788") == "X"  # 표준 문서의 예제
# 음역 겹침 무리
cls = defaultdict(list)
for ch, v in VALS.items():
    cls[v].append(ch)
print("VIN 값 무리:", {k: v for k, v in sorted(cls.items()) if len(v) > 1})
```

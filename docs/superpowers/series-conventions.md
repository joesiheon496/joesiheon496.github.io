# 시리즈 규약 — 글을 쓸 때 매번 확인할 것

7\~9편 스펙마다 §3 에 같은 항목이 반복됐다. 여기 하나로 모은다.
**새 글 스펙의 §3 은 이 문서를 참조하고, 그 글에서 새로 발견한 함정만 적는다.**

## 1. 글의 구조

순서가 고정이다.

```
+++  front matter  +++

> 🎛 데모 안내 (데모가 있으면) + 시리즈 링크

## 어디에 쓰는가        ← 비유. 수식보다 먼저.
## 한 줄 요약            ← 문장 하나의 변주
## (앞 편이 남긴 빚)
...본문 — 실측 표가 주장을 뒷받침한다...
## 정리                  ← 불릿, 각 항목에 숫자
다음 글 예고
---
> 각주 블록: 무엇을 테스트로 고정했는지, 무엇을 아직 안 했는지
```

### 1-1. 🔑 맨 앞에 비유가 온다 (2026-08-05 사용자 지시)

**수학 글은 「어디에 쓰는가」를 일상 상황 비유로 먼저 말한다.** 한 줄 요약보다 위다.

- **기법이 아니라 상황을 말한다.** "경사하강법은 1차 최적화 기법이다"(✗) →
  "안개 속 산에서 내려와야 하는데 지도가 없다"(✓)
- 3\~5줄. 수식·기호 없이
- 그 다음에 한 줄 요약이 이어지면서 비로소 기호가 나온다

**왜**: 1\~9편이 전부 데모 안내 다음에 바로 한 줄 요약으로 들어가, 첫 화면이 기호로
시작했다. 이미 왜 읽는지 아는 독자에게만 통한다.

## 2. 수식

- 인라인은 `\(...\)` — **`$...$` 금지.** 기존 글의 달러 표기가 수식으로 잡힌다
- 블록은 `\[...\]` 또는 `$$...$$`. 둘 다 `hugo.toml` passthrough 와
  `layouts/partials/extend_head.html:37` 의 KaTeX delimiters 에 등록돼 있다
- 블록 수식에 `=` 를 홀로 두지 않는다
- **물결표는 `\~`.** goldmark strikethrough 가 글을 조용히 망친 적이 두 번 있다.
  빌드 후 `grep -rl '<del>' public/` 이 0건인지 확인한다
- `python tools/check-math.py public/posts/<slug>/index.html` 로 렌더 결과를 검사한다

## 3. 날짜

⚠️ **`date` 를 현재보다 뒤로 두지 말 것.** Hugo 가 미래 날짜 글을 **오류 없이 성공**하면서
빼버린다. C++ 글과 9편에서 두 번 걸렸다.

빌드 후 반드시 확인:

```bash
test -f public/posts/<slug>/index.html && echo O || echo X
```

## 4. 데모

- `{{< demo name="<모듈>" panes="2" >}}` — 캔버스 하나면 `panes` 생략
- 순수 수학 모듈(DOM 없음) + 데모 모듈(캔버스 조립)로 나눈다.
  수학 모듈만 `node --test` 로 테스트하고 데모 모듈은 관례상 테스트하지 않는다
- **의존성 0.** 모든 글의 각주가 "의존성 없는 순수 JavaScript" 를 약속한다
- 색은 `themeColors()` 에서만. accent 3개는 하드코딩 hex 이고 CSS 변수가 아니다
  (`.ok` = accent3, `.no` = accent2, `.hi` = accent 파랑)
- 3D 는 `projectPolyline` 을 지난다. 이미지 좌표 뷰는 world 의 y 를 거꾸로 준다
  (`ymin > ymax`)

### 4-1. 한 캔버스에 의미가 다른 선이 둘 이상이면 색을 먼저 배정하고 글에 적는다

7편에서 에피폴라 직선을 지면 격자와 같은 `c.grid` 로 그려 "직선이 엉뚱한 방향" 이라는
신고를 받았다. 수학은 옳았고 색이 틀렸다. **같은 색 두 종류는 없는 것과 같다.**

### 4-2. 데모마다 기본 배치가 달라도 된다 — 대신 글에 적는다

주장하는 것이 다르면 기본값도 달라야 한다. 안 적으면 독자가 같은 그림을 기대하고
어긋난다고 읽는다 (7편 §3-8).

### 4-3. 기본값이 주장하는 대상을 화면에 보이게 둔다

6편에서 소실점이, 7편에서 에피폴이 기본값에서 화면 밖이었다. 수치는 다 맞는데 화면에서
읽을 수 없는 결함이고 **자동 검증으로 안 잡힌다.**

## 5. 측정 규율

**글에 들어갈 숫자는 전부 실측이어야 한다.** 프로토타입을 Node 로 돌려 재고, 그 값으로
스펙 §2 를 쓰고, 그 다음 구현한다. 교과서 문장을 옮겨 적지 않는다.

실적: 6편 3건, 7편 2건, 8편 **축 전체**, 9편 **축의 예측**, C++ 글 **대표 예시 4개**가
이 순서 덕에 뒤집혔다. 구현 후에 쟀다면 데모를 버려야 했다.

### 5-1. 기전이 참인데 크기가 0 인 경우가 있다

8편에서 "무엇을 최소화하는지가 답을 정한다" 가 참인 진술이었으나 대칭 배치에서 효과가
넷째 자리까지 0 이었다. **데모가 성립할 만큼 효과가 큰지를 먼저 재라.**

### 5-2. 지표 자체의 한계를 결과로 오독하지 말 것

- 8편: 2차 수렴 비 \(e_{k+1}/e_k^2\) 는 오차가 1e-14 로 부동소수 바닥에 닿으면 폭발한다.
  스텝 3 이후 인용 금지
- 9편: `arccos` 기반 각 지표는 분해능이 **1.2e-6°** 다
  (\(\delta\theta \approx \sqrt{2\delta c}\)). 왕복·항등 검사는 Frobenius 로 한다
- 데모가 보여줄 숫자와 글에 적힌 숫자가 **같은 설정**에서 나온 값이어야 한다
  (8편에서 정지조건이 달라 스텝 수가 어긋났다)

### 5-3. 배제한 구간을 포함해 적합하지 말 것

8편 초판이 비점근 근거리를 배제한다고 써놓고 지수는 그 구간까지 넣어 적합했다
(\(z^{1.953}\) 대 점근 \(z^{2.014}\)). 테스트가 잡았다.

### 5-4. UB 를 "이렇게 된다" 로 쓰지 않는다

초기화 안 된 메모리, 타입이 틀린 접근, 해제된 버퍼는 실측값이 나와도 규칙이 아니다.
"이 실행에서 이렇게 나왔고 보장은 없다" 로 쓴다.

## 6. 프로세스

7편부터 **스펙(§2 실측 + §3 함정)만 쓰고 plan 은 쓰지 않는다.** 구현은 직접 한다.
커밋 3\~5개 목표. 6편이 spec 549행 + plan 2115행으로 프로세스 문서가 diff 의 61% 였다.

전체 파이프라인(spec → plan → 서브에이전트)은 **여러 글이 의존하는 공유 인프라**를
건드릴 때만 쓴다.

## 8. 저장소

- 작업 디렉터리를 **다른 세션과 공유할 수 있다.** `git checkout` 으로 브랜치를 바꾸면
  그쪽 HEAD 를 빼앗는다. 2026-08-05 에 실제로 발생했다.
  → **`git worktree add` 로 격리된 트리에서 작업한다**
- 새 브랜치에서 작업하고 `--ff-only` 로 병합한다 (병합 커밋 없음)
- 푸시하면 GitHub Actions 가 바로 배포한다. **육안 확인 전에는 푸시하지 않는다**

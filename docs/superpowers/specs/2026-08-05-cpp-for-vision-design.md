## 0. 이 글은 시리즈 밖이다

「컴퓨터 비전 수학 시리즈」는 1편부터 빚을 물려주며 이어지는데 이 글은 그 사슬에 걸리지
않는다. 태그도 다르다 (`C++`, `OpenCV`). 그리고 **데모가 없다** — 인터랙티브 캔버스가
아니라 코드 + 실측 표다. OpenCV 를 실제로 돌려야 하는데 그것은 이 저장소의 "의존성 0"
규약 밖이므로, 측정은 별도로 하고 결과만 글에 옮긴다.

## 1. 글의 축

> **AI 가 코드를 쓰면 병목이 작성에서 검증으로 옮겨간다. 그래서 알아야 할 것은 언어
> 전체가 아니라 「틀렸는데 그럴싸해 보이는」 코드의 목록이다.**

크래시하는 버그는 싸다 — 컴파일러나 segfault 가 알려준다. 비싼 것은 **조용히 틀리는**
것이다. 그림이 나오고 숫자가 나오는데 값이 틀린다. LLM 이 쓴 코드에서 특히 잘 나온다.
문법은 완벽하니까.

### 🔑 이 글의 서론은 내가 틀린 기록이다

이 글을 제안하면서 사용자에게 대표 예시 넷을 들었다. **측정해 보니 넷 다 틀렸거나
과장이었다.** 그 목록이 §3-1 이고, 그것이 이 글의 논지를 스스로 증명한다 —
*이 실패 양식에 대한 글을 쓰는 사람이, 그 규율을 명시적으로 세워둔 상태에서도,
기억에 의존하면 넷을 틀린다.*

## 2. 사전 검증한 수치 — 실측

### 2-1. 🚨 8비트 평균 — **어느 형태가 틀리는지가 반직관적이다**

`uchar` 두 장의 평균. 참값과 비교한다.

| (A, B) | 참값 | `(a+b)/2` | `add` 후 `/2` | `a/2+b/2` | `addWeighted` | 16U 경유 | 순수 C++ | `add` 단독 |
|---|---|---|---|---|---|---|---|---|
| (200, 100) | 150 | **150** | **128** | 150 | 150 | 150 | 150 | 255 |
| (201, 101) | 151 | **151** | **128** | 151 | 151 | 151 | 151 | 255 |
| (255, 255) | 255 | **255** | **128** | 255 | 255 | 255 | 255 | 255 |
| (7, 8) | 7.5 | 8 | 8 | 8 | 8 | 8 | **7** | 15 |

세 가지가 나온다.

1. **`cv::add(a,b,sum); sum/2` 는 입력과 무관하게 128 을 준다.** `add` 가 255 로 포화한
   뒤 나누므로 항상 127.5 → 128 이다. 입력이 무엇이든 같은 답이 나오는데 크래시하지 않는다
2. **한 줄짜리 `(a+b)/2` 는 맞다.** OpenCV 의 `MatExpr` 이 이 식을 `addWeighted` 로
   접어서 중간 포화가 없다. 즉 **두 형태가 같아 보이는데 하나만 맞다**
3. 반올림 방식이 다르다 — (7,8) 에서 OpenCV 계열은 8, 순수 C++ 정수연산은 7

### 2-2. 얕은 복사 — 어디까지 공유하는가

`base.at<uchar>(1,1) = 77` 을 실행한 뒤:

| 만든 방법 | 값 | `data` 포인터 공유 |
|---|---|---|
| `cv::Mat b = base;` | **77** | 예 |
| `base(cv::Rect(...))` | **77** | 예 |
| `base.reshape(1,2)` | **77** | 예 |
| `base.clone()` | 0 | 아니오 |
| `base.convertTo(dst, CV_8U)` (같은 타입) | 0 | 아니오 |

`reshape` 도 공유한다. `convertTo` 는 타입이 같아도 복사한다.

### 2-3. stride — `cols` 로 인덱싱하면 언제 틀리는가

6×5 행렬에서 값이 `y*10+x` 이고, `Rect(1,1,3,3)` ROI 를 잡았다.

```
full: cols=5  step=5  isContinuous=1
roi : cols=3  step=5  isContinuous=0
```

| 접근 | 값 |
|---|---|
| `roi.at<uchar>(1,1)` (참값) | 22 |
| `roi.ptr<uchar>()[1*roi.cols + 1]` | **20** ← 틀린 화소 |
| `roi.ptr<uchar>()[1*roi.step + 1]` | 22 |
| `roi.ptr<uchar>(1)[1]` | 22 |

⚠️ **그리고 평범한 `cv::Mat` 은 정렬 패딩을 넣지 않는다.**

| 폭 | `step` |
|---|---|
| 640 | 640 |
| 641 | 641 |
| 643 | 643 |
| 1000 | 1000 |

즉 `step != cols` 의 출처는 **ROI(와 외부 버퍼)** 이고 "정렬 때문에 패딩이 붙는다" 가
아니다. 이것도 내가 틀린 것 중 하나다 (§3-1).

### 2-4. `resize` 의 화소 중심 규약 — 반 화소가 어디서 생기는가

`src = [0,1,2,...,7]` (1×8, CV_32F) 를 `INTER_LINEAR` 로 16 폭으로 확대:

```
0.00 0.25 0.75 1.25 1.75 2.25 2.75 3.25 3.75 4.25 4.75 5.25 5.75 6.25 6.75 7.00
```

두 가설의 `i=1` 예측: 화소 중심이 정수라면 0.50, 반 화소 규약이라면 0.25.
**실측 0.25** 이므로

\[
\text{src} = (i + 0.5)\,s - 0.5
\]

가 쓰인다. 양 끝은 정의역 밖이라 클램프된다 (0.00, 7.00).

- `INTER_NEAREST` 는 `0 0 1 1 2 2 ... 7 7`
- `warpAffine` **항등변환의 최대 오차 0.00** — 항등은 정확하다
- **0.5 px 이동을 왕복하면 최대 오차 0.50** (원값 범위 0\~7 이므로 전체의 7%).
  선형보간이 두 번 들어가 저역통과가 두 번 걸린다

### 2-5. `at<T>(y,x)` 와 `Point(x,y)`

```
m 은 Mat(3, 6)  — rows=3, cols=6
m.at<uchar>(1, 4)            → 99      (행, 열)
m.at<uchar>(cv::Point(4, 1)) → 99      (x, y) — 순서가 뒤집힌다
m.size() == cv::Size(6, 3)   → true    (폭, 높이)
```

`Mat(rows, cols)` 와 `Size(width, height)` 가 서로 뒤집힌 순서라는 것이 사고의 근원이다.

### 2-6. 초기화하지 않은 `Mat`

`cv::Mat m(8, 8, CV_8U)` 를 200회 만들어 `countNonZero` 를 재면
**200회 전부 0 이 아닌 값**이 들어 있었다. `cv::Mat::zeros` 를 써야 한다.

⚠️ 반대로 0 이 나오더라도 보장이 아니다 — 할당자가 준 메모리에 달렸다.

### 2-7. float 누적은 언제 자리수를 잃는가

`0.1` 을 N 번 더한다.

| N | float | double | 상대오차 |
|---|---|---|---|
| 1,000 | 99.999046 | 100.000000 | 9.54e-6 |
| 100,000 | 9998.5566 | 10000.0000 | 1.44e-4 |
| 10,000,000 | **1087937.0** | 1000000.0 | **8.79e-2** |

1천만 번에서 **8.8% 틀린다** (108만 대 100만).

조건수가 나쁜 최소자승 — 6×6 Hilbert 행렬, 정답이 전부 1 이 되도록 우변을 잡고
`cv::solve(..., DECOMP_SVD)`:

| 정밀도 | 해의 최대오차 |
|---|---|
| `CV_32F` | **1.71e-1** |
| `CV_64F` | 5.83e-11 |

float 로 풀면 답이 1 이어야 하는데 0.83 이 나온다. **9 자리 차이**다.
8편의 κ 이야기가 코드에서 드러나는 지점이다 — 조건수가 나쁜 문제에서 float 는 답을 잃는다.

### 2-8. `at<T>` 의 타입을 틀리면 바이트를 읽는다

`CV_32F` 에 `1,2,3,4` 를 넣고 `at<uchar>` 로 읽으면:

```
0 0 128 63
```

`1.0f` 의 리틀엔디언 바이트 `00 00 80 3F` 다. **컴파일되고 크래시하지 않는다.**

### 2-9. `auto` 와 expression template

```cpp
cv::Mat a = ones*3, b = ones*4;
auto e = a + b;        // Mat 이 아니다 (is_same<decltype(e), Mat> == false)
a.setTo(100);
cv::Mat r = e;         // 여기서 계산된다
```

| | 값 |
|---|---|
| 즉시 계산이었다면 | 7 |
| **실측** | **104** |

`MatExpr` 은 **지연 계산**이라 `a` 를 나중에 고친 것이 결과에 들어간다.

반면 **죽은 지역변수를 참조하는 `MatExpr` 은 이 실험에서 7 을 정상적으로 줬다.**
`cv::Mat` 이 참조 카운트이므로 `MatExpr` 이 잡고 있는 얕은 복사가 데이터를 살려둔다.
→ **OpenCV 의 `MatExpr` 은 Eigen 만큼 위험하지 않다.** 이것도 내가 틀린 것이다 (§3-1).

진짜 dangling 은 **외부 버퍼를 감쌀 때**다.

```cpp
cv::Mat wrap() { std::vector<float> v(16, 5.f); return cv::Mat(4,4,CV_32F, v.data()); }
```

실측 값은 5 로 "정상" 이었지만 (해제된 스택이 아직 덮이지 않았다)
**`m.u == nullptr`** 이다 — 소유권이 없다는 뜻이고, 그것이 판별 방법이다.

### 2-10. 🚨 성능 — "`at<>` 는 10\~50배 느리다" 는 **Debug 빌드 숫자다**

2000×2000 CV_8U 전체 합, 5회 중 최소.

| 접근 | Release `/O2` | Debug `/Od` |
|---|---|---|
| `at<uchar>(y,x)` | 0.74 ms | **18.03 ms** |
| `ptr<uchar>(y)[x]` | 0.48 ms | 2.07 ms |
| `data[i]` 연속 가정 | 2.39 ms | 36.49 ms |
| `cv::sum` | **0.09 ms** | 9.05 ms |
| **at / ptr 비** | **1.52×** | **8.73×** |

세 가지가 나온다.

1. **Release 에서 `at<>` 와 행 포인터 차이는 1.5배뿐이다.** 통설의 10\~50배는 Debug 값이다
   (`at<>` 자체가 Release 대비 24배 느려진다)
2. **`data[i]` 로 평평하게 도는 것이 오히려 느렸다** (0.31×). 행 단위 루프가 벡터화되고
   `total()` 단일 루프는 안 된 것으로 보인다 — **"연속이니까 한 줄로 돌면 빠르다" 가 틀렸다**
3. **진짜 이득은 OpenCV 함수를 쓰는 것이다** — `cv::sum` 이 8.09배. 손으로 루프를 고치는
   것보다 이쪽이 크다

⚠️ Debug 에서 `cv::sum` 이 9.05 ms 로 Release(0.09 ms)의 **100배**다. 디버그 DLL 은
벡터화 경로가 죽는다. **Debug 에서 잰 시간으로 최적화 결정을 내리면 안 된다.**

### 2-11. 안쪽 루프의 `clone`

500 행을 도는 루프. 헤더만 잡기 대 `clone()`:

| | 시간 |
|---|---|
| `m.row(y)` | 0.01 ms |
| `m.row(y).clone()` | 0.37 ms |
| 배율 | **38.5×** |

성능 항목 중 배율이 가장 크다 — §2-10 의 어떤 접근 방식 차이보다 크다.

### 2-12. `imread` 는 BGR 을 준다

`Scalar(0,0,255)` (B=0, G=0, R=255) 로 만든 1×1 을 PNG 로 쓰고 다시 읽으면
`(0, 0, 255)` 다. `split` 후 채널 0 이 0, 채널 2 가 255. `COLOR_BGR2RGB` 를 거치면
`(255, 0, 0)`.

### 2-13. `saturate_cast` 는 **round-half-to-even** 이다

| 입력 | −1.0 | 0.4 | 0.5 | 0.6 | 1.5 | 2.5 | 254.5 | 255.5 | 300.0 |
|---|---|---|---|---|---|---|---|---|---|
| `saturate_cast<uchar>` | 0 | 0 | **0** | 1 | **2** | **2** | **254** | 255 | 255 |
| `(uchar)` C 스타일 | — | 0 | 0 | **0** | **1** | 2 | — | — | — |

`0.5 → 0`, `1.5 → 2`, `2.5 → 2`, `254.5 → 254` — 짝수로 붙는다. 흔히 믿는
"0.5 는 올림" 이 아니다. 그리고 C 스타일 캐스트는 **절단**이라 `0.6 → 0`, `1.5 → 1` 이다.

### 2-14. 0 으로 나누면 타입에 따라 다르다

| | 입력 | 결과 |
|---|---|---|
| `CV_32F` `a / b` | `[1,2,3] / [1,0,3]` | `1, inf, 1` |
| `CV_8U` `cv::divide` | 같음 | `1, 0, 1` |

float 는 `inf` 를 그대로 내보내고 정수는 0 으로 막는다. **같은 코드가 타입에 따라 다르게
행동한다.**

### 2-15. MSVC 는 BOM 없는 UTF-8 소스를 시스템 코드페이지로 읽는다

이 프로토타입을 처음 빌드할 때 실제로 걸린 것이다. 한글 주석·문자열이 든 UTF-8 소스를
`/utf-8` 없이 `cl` 로 컴파일하면 CP949 로 해석되어

```
error C4430: 형식 지정자가 없습니다
error C2001: 상수에 줄 바꿈 문자가 있습니다
```

같은, 원인과 무관해 보이는 오류가 난다. 일부 한글의 둘째 바이트가 `0x5C`(`\`) 라서
문자열 리터럴이 닫히지 않는다. **`cl /utf-8`** 이 해결책이다.

## 3. 사전에 잡은 함정

### 3-1. 🚨 내가 사용자에게 말한 대표 예시 **넷이 틀렸다** — 이 글의 서론

이 글을 제안하면서 든 예시와 실측:

| 내가 말한 것 | 실측 | 무엇이 틀렸나 |
|---|---|---|
| `(a+b)/2` 가 200·100 에서 **127** | **150** | `MatExpr` 이 `addWeighted` 로 접는다. 진짜 범인은 `add` 후 `/2` = **128** |
| `step != cols` 는 **정렬 패딩** 때문 | 640·641·643·1000 전부 패딩 없음 | 출처는 **ROI**(와 외부 버퍼)다 |
| `at<>` 루프가 **10\~50배** 느리다 | Release **1.52배** | 10\~50배는 **Debug** 값이다 |
| Eigen 식 `auto` **dangling** 이 대표 함정 | OpenCV `MatExpr` 은 refcount 로 살아남아 정상값 | 진짜 함정은 **지연 계산**(104 대 7)과 **외부 버퍼 감싸기** |

네 개 다 "널리 알려진 사실" 로 알고 있던 것이고, 재보니 달랐다. 이것을 글의 서론으로
쓴다 — **논지를 주장하는 대신 스스로에게 적용해 보인다.**

### 3-2. Eigen 이 이 기계에 없다

`C:\opencv` 는 있으나 Eigen 은 없다 (헤더 온리라 내려받으면 되지만 네트워크 작업이고
사용자 승인 사항). 따라서 **Eigen 항목은 이 글에서 뺀다.** 열 우선 대 행 우선,
`auto` 와 expression template 은 OpenCV `MatExpr` 로 같은 교훈을 낼 수 있고
(§2-9), 그 편이 의존성도 하나로 줄어든다.

→ Eigen 을 다루려면 별도 글이고, 그때 Eigen 을 받아 **직접 재고** 쓴다.
이번 글에서 Eigen 을 "아마 이럴 것이다" 로 쓰면 §3-1 을 또 반복하는 것이다.

### 3-3. 시간은 배율만 인용한다

§2-10·§2-11 의 절대 ms 는 이 기계 값이다. 글에는 표를 그대로 싣되 환경 블록(§2 머리)을
함께 두고, 본문 주장에는 **배율만** 쓴다.

### 3-4. 버전을 명시한다

`MatExpr` 이 `(a+b)/2` 를 접는 것은 **구현 세부**다. OpenCV 4.5.4 에서 관측한 것이고
다른 버전에서 다를 수 있다. "OpenCV 4.5.4 에서" 를 붙인다. §2-1 의 결론은 그래서
"이 형태가 맞다" 가 아니라 **"두 형태가 같아 보이는데 다르게 행동한다"** 로 쓴다 —
그것이 버전에 안전한 교훈이다.

### 3-5. UB 를 "이렇게 된다" 로 쓰지 않는다

§2-6(초기화 안 된 Mat), §2-8(타입 틀린 `at`), §2-9(죽은 버퍼)는 전부 UB 이거나
미정의에 가깝다. 실측값이 나왔다고 그것이 **규칙인 것처럼 쓰면 안 된다.**
"이 실행에서 이렇게 나왔고, 보장은 없다" 로 쓴다. §2-9 의 죽은 버퍼가 5 를 준 것이
정확히 그 예다 — 운이 좋았을 뿐이다.

### 3-6. 검증 다섯 가지가 이 글의 결론이다

코드를 못 써도 되지만 **검사는 직접 설계할 수 있어야** 한다. 종류가 다섯이다:

| 검사 | 이 글에서 실제로 쓴 예 |
|---|---|
| 왕복 | `resize`/`warpAffine` 0.5 px 왕복 → 오차 0.50 (§2-4) |
| 알려진 정답 | Hilbert 최소자승의 답은 전부 1 (§2-7) |
| 불변량 | `data` 포인터 비교로 공유 여부 판정 (§2-2), `m.u == nullptr` (§2-9) |
| 극단·퇴화 | (255,255) 평균, 0 으로 나누기 (§2-1, §2-14) |
| 두 경로 대조 | `at` 대 `ptr` 대 `step`, float 대 double (§2-3, §2-7) |
| 차원·단위 | `Mat(rows,cols)` 대 `Size(w,h)` (§2-5) |

⚠️ 여섯 개다. 위 목록을 글에 쓸 때 다섯이라고 세지 말 것 — 이전 대화에서 다섯이라고
말했으나 실제로 쓴 것은 여섯 종류다.

### 3-7. 이 저장소 규약
